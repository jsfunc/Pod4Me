H1  Radio outage destroys the rewind buffer ............... FIXED in the recorder; NEEDS PHONE

N1  MEDIUM  A never-working station is retried for ~5 minutes, then reported misleadingly
    Where: RadioBuffer capture loop (retryLimit 24, backoff up to 15 s);
           PlaybackService.recoverPlaybackError (radio branch returns without reporting);
           RadioScreen.radioStatus ("Station unavailable · Buffer kept · Back to live retries").
    What:  The reconnect logic does not distinguish "connection lost after audio" from "never
           received audio". A mistyped custom URL, an HTTP 404/403, or a station's web page
           shows "Reconnecting…" for about 5 min 15 s (probes P1/P2: 25 requests; an HTML page
           is re-downloaded each time). It then shows "Station unavailable · Buffer kept"
           although nothing was buffered, and no error message (probe P4). Before the
           modifications this failed immediately with "Could not play X…".
    Fix:   If no segment was ever appended, stop after 2–3 attempts, or immediately on an HTTP
           4xx or an HTML response, then report the old error (handlePlaybackError). Show "Buffer
           kept" only when window.hasAudio.

N2  LOW     Any podcast error blames the download, permanently
    Where: PlaybackService.recoverPlaybackError (store.playbackError for every error code);
           LibraryStore.playbackError (the error column is cleared only by download()).
    What:  Errors unrelated to the file, such as ERROR_CODE_AUDIO_TRACK_INIT_FAILED (5001, seen
           with audio-route/Bluetooth problems), stamp "This download could not be played.
           Delete it and download it again." The message stays after the episode later plays
           normally (probe P6).
    Fix:   Record the message only for codes 2000–4999 (I/O, parsing, decoding), and clear the
           episode's error when it plays successfully (first progress save or STATE_READY).

N3  LOW     Resume does nothing at the end of a finished radio window (code reading)
    Where: PlaybackService.togglePlayback: for liveStation it only calls prepare() when IDLE,
           then play().

           has played out, the player is in STATE_ENDED, and play() without a seek has no effect.
           Resume (Player tab, mini-player, notification, headset) then appears dead; only Back
           to live works. The status text points to Back to live, which mitigates it. Probe P5
           could not reach STATE_READY under Robolectric, so this is not demonstrated.
    Fix:   In togglePlayback, if liveStation != null and the state is ENDED, call goLive().
           Check it on the phone with check 53.

New problems / further improvements
-----------------------------------
N5  MEDIUM  "Invalid station" is terminal even in the middle of a broadcast (regression of H1)
    Where: RadioBuffer.kt:72 (`|| e is InvalidStation`), the request() 4xx mapping at line
           168, and the HTML detection at line 110.
    What:  N1's fast-fail is meant for a station that never worked. It also applies after
           hours of good capture. Situations it ends capture in:
             - Icecast/Shoutcast return 404 while the studio encoder reconnects (common
               during station maintenance);
             - hotel/train Wi-Fi portals answer with an HTML page (the very scenario H1 was
               about);
             - CDNs return 404/410 for an HLS segment that lags or has rotated out, or 403
               when a URL token expires (the outer loop would re-fetch the master playlist
               and get a fresh token).
           Probes Q1/Q2/Q3: UNAVAILABLE after one such response, with 23 retries unused. The
           buffer is kept, but the user must notice and press Back to live.
    Fix:   Treat InvalidStation as terminal only while !window.hasAudio. Otherwise count it as
           an ordinary retry: `if (++attempts > limit || (e is InvalidStation &&
           !window.hasAudio))`. For HLS, a 404/410 on a single segment could also skip that
           segment (gap → discontinuity) instead of aborting the playlist. Add tests:
           audio → 404 → audio recovers; audio → HTML → recovers; one segment 404 → capture
           continues.

N6  LOW     Session extras are rebroadcast every second, forever
    Where: PlaybackService.onCreate, the `while (isActive) { delay(1000); … publishExtras() }`
           loop.
    What:  The loop runs for the service's whole life, playing or not, with or without a
           timer. Each iteration takes the operations lock and calls setSessionExtras. In Media3
           1.8 (javap) that is sent to every connected controller and to the platform session.
           So system UI, Bluetooth and any Wear/Auto controller receive an extras-changed IPC
           every second, which costs battery and adds binder churn. The app UI does not need
           it: MainActivity already polls PlayerClient.refresh() every 500 ms.
    Fix:   Publish an absolute SLEEP_DEADLINE (elapsedRealtime is device-wide, so the UI can
           compute what remains) once when the timer is set or changed. Publish extras only
           when a value changes. Replace the loop with one job that is scheduled with
           delay(deadline − now) and cancelled with the timer.

N7  LOW     A timer that expires while paused, with the phone asleep, stops the next resume
    Where: checkSleepTimer, the 1-s loop, and togglePlayback's `if (checkSleepTimer()) return`.
    What:  Example: a 60-min timer, a headset pause at minute 20, then the screen goes off.
           While paused ExoPlayer holds no wake lock, so the main-looper delay is frozen in
           deep sleep and the timer never fires. The next morning a headset or notification
           Play resumes playback; within ≤1 s the loop sees the expired deadline and pauses
           again. Through the app's own button, togglePlayback swallows the first press
           instead. Code reading only; Robolectric cannot model deep sleep.
    Fix:   When the deadline is found to have passed while the player was not playing, cancel
           the timer silently, without pausing, and let the Play go through. Alternatively,
           count only playing time (a product choice; the handover says pauses do not reset
           the timer, which this keeps).

N8  LOW     Mark Unheard does not undo the 3-day Heard deadline
    Where: LibraryStore.setHeard (sets expiry on Heard; on Unheard only resets the position).
    What:  Heard is also set automatically by seeking past 95%. With the 3-day rule, a
           download marked Heard by mistake is deleted 3 days later even after the user marks
           it Unheard (probe Q6: 30.0 → 3.0 → 3.0 days). The Info screen shows the date, but
           nothing hints that Unheard leaves it unchanged.
    Fix:   On Heard→Unheard of a downloaded episode, restore
           Policy.downloadExpiry(downloaded, feed.expiry_days). Use the original download time,
           so this cannot extend a file indefinitely. Needs a product confirmation; record it in
           the handover.

N9  LOW     An old radio notice hides later statuses
    Where: RadioScreen.radioStatus (the radioNotice branch comes before PAUSE_LIMIT,
           UNAVAILABLE and RECONNECTING); PlaybackService clears radioNotice only on
           goLive/startRadio/close.
    What:  After "The paused position expired…", later outages still show that notice instead
           of "Reconnecting…" or "Station unavailable" (probe Q4), for as long as the station
           stays loaded.
    Fix:   Put the notice after the buffer-status branches, or clear radioNotice on the next
           RadioBuffer status change, or after about 10 s of playback.

N10 LOW     A move to a previously unsubscribed feed fails forever, with a misleading message
    Where: LibraryStore.applyRefresh (the duplicate check covers all feeds rows, including
           subscribed=0).
    What:  Unsubscribed feeds keep their row and URL. If feed A permanently moves to B and the
           user once unsubscribed from B, every refresh of A fails with "This feed moved to an
           existing subscription. Review both subscriptions…". There is no B subscription to
           review (probe Q5), and A goes into the failed-feeds dialog on every refresh.
    Fix:   Say "…to a feed you previously unsubscribed from (B)". Offer, or simply do, the
           rename: keep A's id, history and settings, and move B's leftover episodes/history
           only if B has any. Alternatively keep A's URL and stop reporting the move as a
           refresh failure.

N11 LOW     Wrong wording for some non-file podcast errors
    Where: PlaybackService.recoverPlaybackError, the final handlePlaybackError message.
    What:  Every code outside 2000–4999 gets "Audio output was interrupted. Check your speaker or
           Bluetooth connection…". That fits 5xxx (audio sink) only. It is wrong for:
             - 1000 unspecified, 1003 timeout, 1004 failed runtime check;
             - 6xxx DRM;
             - 7xxx video frame processing (a downloaded video episode).
    Fix:   Use the output wording for 5000–5999 only, and a neutral "Playback stopped
           unexpectedly. Tap Play to retry." otherwise.

N12 LOW (security)  A feed can be permanently downgraded from HTTPS to HTTP
    Where: FeedClient.permanentRedirect and LibraryStore.applyRefresh (new-feed-url).
    What:  OkHttp follows https→http redirects, and cleartext is allowed (S2). A misconfigured
           host's 301 https→http, or a new-feed-url with http://, is stored permanently. Every
           later refresh then runs in cleartext, where a network attacker can rewrite the feed,
           including its new-feed-url, and move the subscription to a feed of their choice.
    Fix:   Refuse to persist a move that changes https to http. Keep the old URL and still use
           the fetched content.

N13 INFO / polish
    a) The specific radio failure reason is lost: "Use the station's direct audio URL, not its
       web page" and "Radio server returned HTTP 403" stay inside RadioWindow.fail. The user sees
       the generic "Could not play X…". Pass the buffer's last failure message to
       handlePlaybackError for the no-audio case. This fits custom-station setup, together with
       the I3 "Test" button idea.
    b) SubscriptionDialog treats input without "://" as a name search.
       "feeds.example.com/podcast.xml" or "podcasts.apple.com/fr/podcast/x/id123" pasted
       without a scheme is therefore searched instead of subscribed. Treat dotted, space-free
       input containing "/" as https://….
    c) confirmImport subscribes strictly one feed at a time. Each fetch can take up to the
       3-minute call timeout, so 100–1000 entries can block the app (busy) for a long time with
       no progress. Reuse FeedRefresher-style 4-way concurrency and the header counter
       ("Importing 12/80").
    d) The End-of-episode countdown shows media time (duration − position), not wall-clock time.
       At 2× it overstates the remaining time by half. Divide by the playback speed.
    e) refresh(feed) for a single feed replaces failedIds, which silently drops the list from an
       earlier full refresh. Merge the lists, or keep single-feed refresh out of the dialog.
    f) The OPML importer reads only the exact attribute "xmlUrl". A few exporters write "xmlurl"
       or "url" (type="link"). Accept these case-insensitively.
    g) Conditional GET means unchanged feeds are no longer re-parsed. When a future release
       changes FeedParser output (as schema 7 did for byte_size), its migration must clear
       feeds.etag/last_modified, or the new fields never appear for quiet feeds. Add this to the
       handover's regression traps.
    h) Not done and listed as remaining discussion:
         - show the stored last_refreshed (I9);
         - skip silence (I6);
         - accent folding in the station picker (I10);
         - disable the video track without a surface (I8);
         - split PodApp.kt (I11).

N12b LOW (security)  A cleartext hop can still move a secure subscription
    Where: LibraryStore.applyRefresh (the downgrade check compares only the scheme of the final
           proposed URL) and FeedClient (OkHttp follows https→http redirects; FeedResponse does
           not say whether the body arrived in cleartext).
    What:  Suppose an https feed redirects to http, for example during a host misconfiguration.
           The body is then fetched in cleartext, and its new-feed-url is trusted. Likewise, a
           301/308 injected on the cleartext hop toward an HTTPS URL becomes permanentUrl. Either
           way, a network attacker on that hop can permanently re-point the subscription to an
           HTTPS feed they control (probe Q7, both forms). The direct https→http move is
           correctly refused.
    Fix:   In FeedClient, record whether any response in the redirect chain was http. When the
           subscription is https and any hop was http:
             - ignore new-feed-url;
             - do not persist any permanentUrl;
             - keep using the content, as now.
           Simpler: build the feed OkHttpClient with followSslRedirects(false) and report "This
           feed redirects to an insecure address" for https subscriptions.

N14 INFO  A silently kept address after a move to a previously unsubscribed feed
    With a 301 the old address keeps redirecting, so content stays current. With
    new-feed-url alone, publishers often freeze the old feed, and the subscription then just
    stops getting episodes. Fix: show a non-error line in feed settings: "Publisher moved this
    feed to <B>, which you unsubscribed from earlier." Optionally add a one-tap "Switch to new
    address", keeping both histories.

N15 INFO  Radio startup error wording

        connection or direct stream URL…" (a capital letter mid-sentence, and the advice
        repeated);
      - for DNS failures, OkHttp's raw text ('Unable to resolve host "…": No address
        associated with hostname').
    Fix: map the known causes (HTML page, HTTP 4xx/5xx, DNS, timeout) to short phrases, and
    keep the raw message only as a fallback.
