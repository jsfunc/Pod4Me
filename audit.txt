Overall assessment
------------------
The podcast core (storage, migrations, deletion protection, progress epochs, backup and restore,
parsing, sharing) is in good shape. The defensive work from the earlier audits holds, and the
automated suite covers it well. No security regression was found.

The weak spot is the newest code, live radio with rewind. The rewind design (capture upstream
into a private rolling HLS window) is sound, but it has no recovery path. One upstream
interruption ends the capture permanently, then deletes the buffered half hour as well (H1). On a
phone that means leaving Wi-Fi, a tunnel, or a single failed HLS request. Before rewind (1.0.13–
1.0.17), ExoPlayer's own load retries covered this case, so this is a resilience regression.

The second-largest risk is data cost: paused radio keeps downloading indefinitely (M1), and
episode downloads/streams carry no size information (M3). One of the seeded sample episodes is
3 GB, and downloads are allowed on mobile data.

Severity: HIGH = will bite in normal use, or a real security hole; MEDIUM = incorrect behaviour in
a reachable situation, or real cost to the user; LOW = robustness, consistency, quality;
INFO = worth knowing. "Improvement" items (section I) are suggestions, not defects.


FINDINGS — BUGS AND UNDESIRABLE BEHAVIOUR
=========================================

H1  HIGH    Any upstream radio interruption kills playback and discards the whole rewind buffer
    Where: playback/RadioBuffer.kt:77-79 (capture job ends on the first exception, calls
           window.fail), :161 (one failed HLS playlist poll, or any segment/key/init fetch at
           :141-143, throws out of captureHls); playback/RadioWindow.kt:68 (once failure is set,
           read() throws for EVERY name, including already-buffered segments); PlaybackService.kt
           :97-102 → handlePlaybackError :193-212 (stop, clearMediaItems, closeRadioBuffer →
           directory deleted).
    What:  There is no reconnect anywhere in the capture path. Concretely:
           - progressive MP3/AAC: Wi-Fi→mobile handover, a tunnel, or a server stall longer than
             the 25 s read timeout ends the stream (EOFException/IOException);
           - HLS: a single 5xx/timeout on the playlist poll or on one segment ends the capture.
           The local window then refuses even old segments, so ExoPlayer's playlist reload fails
           after its default retries, onPlayerError fires and the service unloads the station and
           deletes the cache. The user sees "Could not play X…" and loses the 30-minute rewind
           window. This also happens when the user is paused or listening 20 minutes behind
           live, where the buffered audio is still perfectly playable.
    Fix:   (1) Keep serving existing segments after a capture failure; make read() throw only
           for the live edge once the buffer is exhausted. (2) Retry upstream with bounded
           backoff (e.g. 1, 2, 4, 8, 15 s, then every 15 s for a few minutes), append with
           discontinuous=true after reconnecting (HLS already supports discontinuity; for MP3/AAC
           set it on the first chunk after reconnect), and surface "Reconnecting…" through the
           existing Buffering status. (3) Let a transient HLS fetch failure skip that poll rather
           than abort. Add RadioBufferTest cases for "upstream drops, then recovers" and
           "upstream drops while paused".

H2  MEDIUM  Video streaming fails when the enclosure redirects between http and https
    Where: playback/PlaybackService.kt:53-54 (DefaultDataSource.Factory(this) → default
           DefaultHttpDataSource.Factory, allowCrossProtocolRedirects=false, verified by javap).
    What:  STREAM_VIDEO plays ep.audioUrl through ExoPlayer's HTTP stack, which refuses
           http→https or https→http redirects. Many feeds still publish http:// tracking
           prefixes (podtrac, blubrry, chartable-style chains) that redirect to an https CDN.
           Such episodes fail with "The video stream could not be played…", while Download of
           the same URL works (DownloadManager follows the redirect). The three seeded feeds are
           unaffected (all hops are HTTPS→HTTPS, probed today), which is why this has not shown
           up.
    Fix:   DefaultDataSource.Factory(this, DefaultHttpDataSource.Factory()
           .setAllowCrossProtocolRedirects(true).setUserAgent("Pod4Me/…")), or the
           media3-datasource-okhttp module with the app's OkHttpClient (same Media3 version, so
           still no upgrade). Add a test with a MockWebServer http→https redirect.

M1  MEDIUM  Paused radio keeps downloading without limit
    Where: PlaybackService.togglePlayback :331-335 (pause leaves the capture running);
           RadioBuffer.kt capture loop; RadioWindow only bounds what is kept, not what is fetched.
    What:  Handover-accepted behaviour is "Pause keeps capture running". Nothing stops it,
           though. A station paused and forgotten keeps streaming for as long as the service
           lives: about 58 MB/hour at 128 kbps, on mobile data too. Once the paused position is
           older than 30 minutes, the extra data has no use. On resume, the onPlayerError branch
           for ERROR_CODE_BEHIND_LIVE_WINDOW jumps to the oldest retained audio anyway. While
           paused, ExoPlayer drops its wake/Wi-Fi locks, so with the screen off the capture can
           also stall and hit the H1 failure. Resuming then shows an error instead of the buffer.
    Fix:   Stop capturing once paused for longer than the window, or after a fixed limit such as
           30 minutes. Keep the station loaded so Resume reconnects at live. Optionally keep a
           partial wake lock only while capturing during a pause.

M2  MEDIUM  One unplayable file stops the whole playlist
    Where: PlaybackService.kt:97-103 → handlePlaybackError :193-212.
    What:  When an auto-advanced or Next/Previous item fails, playback stops and everything is
           unloaded with a generic message. Examples: corrupt or truncated download, or a
           "Previous" item whose file expired or was deleted since it was put in the timeline;
           rebuildUpcoming refreshes only the items after the current one. The queue and context
           are not consumed, but the user must start again by hand. This is common enough in
           practice: a partial download that passed the HTML sniff, or an unsupported codec.
    Fix:   For local podcast items, mark the failing episode with an error ("This download
           could not be played"), remove it from the timeline, and continue with the next
           playable item. Stop only when nothing playable remains. Rebuild the preceding items
           too when files disappear.

M3  MEDIUM  Downloads and streams give no size information; multi-gigabyte downloads go over
            mobile data in one tap
    Where: FeedParser ignores enclosure length; LibraryStore.download :255
           (setAllowedOverMetered(true)); seeded feeds LibraryStore.kt:81-85.
    What:  The seeded "This Week in Tech (Video)" HD feed has 3.0 GB episodes (measured today).
           One tap on Download starts it on mobile data with no warning, and storage space is
           only checked by DownloadManager. Streaming the same file in the background is equally
           costly. Mobile data on downloads is an accepted rule; the missing size display and
           confirmation are the problem.
    Fix:   Store <enclosure length> (schema 7 migration, nullable) and show it beside the
           duration ("23min · 48 MB"). Ask for confirmation above a threshold (e.g. 500 MB) or
           when the network is metered. Consider seeding TWiT's smaller video variants.

L1  LOW     Every return to the foreground and every rotation reloads the whole library
    Where: MainActivity.kt:35-37 (repeatOnLifecycle(STARTED) { model.onLaunch(); connect() });
           AppModel.onLaunch :57-60; LibraryStore.initialize :78 (write(force=true) →
           full snapshot + catalogueRevision+1).
    What:  Each STARTED (home→back, unlocking, rotation) re-runs the full launch work in this
           order: full SQLite snapshot, seeding checks, radio prefs read, DownloadManager
           reconcile, expiry, storage scan. Only then does the player controller connect.
           Effects: (a) the revision bump re-sorts every list and rebuilds an open feed-search
           index (FeedSearchState.kt:17 keys on revision), and re-reads open Info notes;
           (b) after rotating a playing video, the surface stays black and the Live Play
           buttons stay disabled (playback.connected=false) until all of that finishes;
           (c) expiry deletion runs much more often than "on launch".
    Fix:   Connect the controller first. Run initialize/seeding once per process (the
           Application already initializes the store). Run reconcile/expiry/storage once per
           foreground session, and not on a configuration change (check isChangingConfigurations
           or move it to ProcessLifecycleOwner ON_START). Don't bump catalogueRevision when the
           snapshot is unchanged.

L2  LOW     HLS radio picks the lowest-bitrate variant
    Where: RadioBuffer.kt:123 (variants … minByOrNull { bitrate }).
    What:  For multivariant playlists without a separate audio rendition, the capture
           deliberately takes the worst quality (often 48 kbps HE-AAC). Today's catalogue HLS
           URLs are already media playlists, so this only affects custom URLs.
    Fix:   Prefer the highest audio-only variant up to ~192 kbps (lower on metered networks if
           desired).

L3  LOW     Common radio playlist wrappers (.m3u / .pls) are rejected
    Where: RadioBuffer.kt:50-51 (any "mpegurl" content type → HLS parser), RadioFrames.
    What:  Many station sites publish "listen.m3u" or ".pls" files that simply point to an
           Icecast URL. A plain .m3u without #EXTM3U fails in HlsPlaylistParser. An extended
           M3U wrapping an endless Icecast stream is treated as a live HLS playlist whose single
           "segment" never ends, so it fails at "Radio segment is too large" after 8 MB. A .pls
           reaches RadioFrames and fails as "not an MP3 or AAC stream". All of these end in the
           generic "Could not play…" message.
    Fix:   Before the HLS parser: if the body has no #EXT-X-TARGETDURATION (or is a .pls),
           extract the first http(s) entry and restart with it (one level only).

L4  LOW     Several real-world pubDate forms become "Date unknown"
    Where: domain/FeedParser.java:230-262. Probe results (UNKNOWN = parsed as 0):
           "+01:00" offsets (Tue, 03 Nov 2026 10:00:00 +01:00), "Z", CET/CEST/BST/MET/AEST
           abbreviations, "Sept", French "déc"/"févr" without the dot, and
           "2026-11-03 10:00:00" (space instead of T). These parse correctly: +0100, GMT/UT/
           US zones, no seconds, "mar., 03 nov. 2026", ISO with offset.
    What:  Undated episodes sort last in Latest and break the "most recent past" anchor.
    Fix:   Normalize before parsing: "+hh:mm"→"+hhmm", "Z"→"+0000", add CET/CEST/BST/MET/EET
           to the zone map, strip trailing dots from month tokens and map "sept"→"sep", and
           accept "yyyy-MM-dd HH:mm[:ss]". Add the probe strings to CoreChecks.

L5  LOW     Radio subscriptions are all-or-nothing on load
    Where: data/RadioPreferences.kt:49-54 (each saved row goes through RadioStation.create).
    What:  If one stored station stops passing validation (for example a stricter rule in a
           later version), read() throws and the whole Live list stays empty. START_RADIO and
           resumption also fail.
    Fix:   Skip, and report once, rows that fail validation instead of failing the whole list.

L6  LOW     Radio is typed as speech: navigation prompts pause it instead of ducking it, and
            it drifts behind live
    Where: PlaybackService.kt:56 (CONTENT_TYPE_SPEECH for everything); Media3 pauses on
           duckable focus loss for speech (javap-verified).
    What:  Correct for podcasts. For live radio, each GPS prompt or notification sound pauses
           the stream, and resuming continues from the paused point inside the rewind window.
           After a drive with navigation, the radio is minutes behind live without the user
           noticing. "Back to live" exists, but nothing prompts for it.
    Fix:   Set CONTENT_TYPE_MUSIC (duck) for radio, and SPEECH back for podcasts. Optionally
           make speech/music a per-station choice.

L7  LOW     Media-button resumption after a radio or video session keeps the network wake mode
    Where: PlaybackService.onPlaybackResumption podcast branch :131-142 (no setWakeMode), and
           stopPlayback :240-256 (does not reset it).
    What:  After Stop on radio or video, a headset Play resumes a local podcast while
           WAKE_MODE_NETWORK is still set, holding a Wi-Fi lock for no reason. startEpisode
           resets it; the resumption path does not.
    Fix:   setWakeMode(C.WAKE_MODE_LOCAL) in the podcast resumption branch (and in stopPlayback).

L8  LOW     The service and the view model do O(library) work on the main thread at every
            progress save
    Where: PlaybackService.kt:183-185 (library.map { queue to episodes.filter{…}.map{…} } on
           Dispatchers.Main.immediate); AppModel.kt:46-51 (episodes → Triple list on Default).
    What:  While playing, every 5-second save publishes a new Library, and both collectors
           rebuild per-episode lists. Unnoticeable with hundreds of episodes; measurable at the
           10,000+ episodes the store is designed for.
    Fix:   Expose a small derived flow from the store (queue + downloaded-ids revision) and
           collect that instead.

L9  LOW     HLS keys and init sections are refetched for every segment
    Where: RadioBuffer.kt:141-143.
    What:  With encrypted or fMP4 radio, each 4-10 s segment triggers extra HTTP requests for
           the same key/init URI. This doubles the requests and adds failure points (see H1).
    Fix:   Cache the last key/init bytes by resolved URI (and byte range).

L10 LOW     Completed-download notifications accumulate
    Where: LibraryStore.download :256 (VISIBILITY_VISIBLE_NOTIFY_COMPLETED).
    What:  Each finished download leaves its own system notification, and the app already shows
           the state in Library. After a refresh session this is a pile of notifications to
           swipe away.
    Fix:   Use VISIBILITY_VISIBLE (progress only), or one summary notification of your own.

L11 LOW     Carried-over minor items, still present
    - B16: one LazyListState per distinct search string, never evicted (PodApp.kt:200).
    - Duplicate subscriptions differing only by a trailing slash, or by http/https, are not
      detected (AppModel.importFeeds compares exact strings).
    - FeedParser.httpUrl reports internationalized (non-ASCII) host names as "…without embedded
      credentials", which is misleading. Convert them with IDN.toASCII, or word the message
      generically.


SECURITY
========
No new issue. The new surfaces were checked:
  - Radio buffer: files are named from a local counter, and the DataSource only serves names
    present in the window, so no path traversal. The pod4me-radio:// URIs are checked for their
    random per-buffer authority. Playlist/segment/key URLs go through FeedParser.httpUrl
    (http/https, no credentials) with 1 MiB playlist and 8 MiB segment caps. Abandoned caches are
    deleted. A hostile playlist can make the phone request arbitrary http(s) URLs, including LAN
    addresses. This is inherent to streaming and equivalent to enclosures; acceptable for
    private use.
  - Video streaming: limited to episodes flagged as video, URL re-validated in activate(), and
    only the app's own controller can send STREAM_VIDEO/START_RADIO (onConnect/onCustomCommand
    package checks unchanged).
  - YouTube rows are never fetched. ACTION_VIEW uses a re-normalized https://www.youtube.com URL.
Carried over, unchanged by decision:
  S1  MEDIUM  Signing key is a renamed debug key with default password; build-apk.sh:15-24 still
              copies ~/.android/debug.keystore when the personal key is missing, minting a new
              certificate. Excluded by the user on 2026-11-01. Still recommended: make a missing

  S2  LOW     usesCleartextTraffic=true app-wide, and OkHttp follows https→http redirects.

  S7  INFO    CI still runs check_schema.py without -I; harmless on a runner.


IMPROVEMENTS (clear, small to medium; ordered by value for a personal podcast/radio app)
=========================================================================================

I1  Add subscription by name. "Add subscription" accepts only a URL. PodcastDiscoveryClient
    already performs rate-limited Apple searches. If the input is not a URL, search
    itunes.apple.com/search?entity=podcast and list the results with Subscribe. Also accept
    podcasts.apple.com/…/id123 links via /lookup. This is the most common way people add
    podcasts.

I2  OPML import and export. Every other podcast app (AntennaPod, Pocket Casts, Podcast Addict,
    Apple via third-party tools) exports OPML, and the Pod4Me web app already imports it. Keep
    the text format as the default export.

I3  Radio resilience: H1's reconnect, plus "Reconnecting…" status, M1's paused-capture cap,
    L2/L3, and a "Test" button for custom URLs (fetch 2 s and show "MP3 128 kbps OK").

I4  Faster, lighter refresh. Refresh fetches feeds one after another, each up to 3 minutes,
    always re-downloading and re-parsing the full feed. Suggested changes:
      - 4 concurrent fetches (Semaphore), with "Refreshing 12/40" in the progress bar;
      - store ETag/Last-Modified per feed and send If-None-Match/If-Modified-Since; skip
        parsing on 304 (schema 7, same migration as M3);
      - persist permanent redirects (301/308) and <itunes:new-feed-url> as the feed's new URL,
        so feeds survive publisher moves.

I5  Sleep timer (15/30/45/60 min, end of episode). A few lines around player.pause() in the
    service; the most-requested podcast player feature missing here.

I6  Playback niceties:
      - restart from the beginning when Play is pressed on an episode at ≥95% (currently resumes
        in the last minute: Policy.resumePosition only resets at ≥100%);
      - optional "skip silence" (ExoPlayer setSkipSilenceEnabled), global like speed;
      - Mini-player for radio: offer Pause (keeps rewind) next to Stop. Stop currently wipes the
        30-minute buffer, which is easy to do by accident now that rewind exists. This changes
        a recorded UI decision, so ask first.

I7  Backlog management in Latest. Every never-played episode shows "Unheard", and non-downloaded
    episodes cannot be marked heard. Add "Mark heard" in Info for any episode and "Mark all older
    as heard" per feed. Optionally add a "hide heard" toggle in Latest. This makes the
    Heard/Unheard text informative.

I8  Video: a fullscreen/landscape mode (the surface is only a 16:9 box inside the scrolling Player
    column). Keep the Activity across rotation while video plays (handle orientation config
    changes, or keep the surface outside the recreated Activity), which also removes L1(b).
    Disable the video track when no surface is attached, to save decoding and, for streams,
    some of the bandwidth.

I9  Show more feed metadata cheaply: enclosure size (M3), and "last refreshed" time per feed (the
    refresh marker exists; a timestamp column would make stale or failing feeds visible).

I10 Station picker search: fold accents ("cherie" → "Chérie FM", "oui" → "OÜI FM"). FeedSearch
    already has the normalization code.

I11 Maintainability:
      - ui/PodApp.kt is 995 lines with many 150-250-character lines. Split it per screen
        (Library/Latest list, Feeds, Queue, Player, dialogs). The radio code already shows the
        pattern.
      - "unheard"/"heard"/"4ever" literals appear in ~10 places, and page names ("Library",
        "Latest", …) are bare strings. Use constants or an enum.
      - tools/build-apk.sh hard-codes versionCode/versionName (lines 34, 45-47). Read them from
        aapt output or Gradle so a version bump is a one-file change.
      - 34 lint warnings, mostly UseKtx (18). Fixing ModifierParameter/ObsoleteSdkInt is free;
        the dependency notices go with the deferred upgrade review.
      - The seeded sample feeds and YouTube channel (LibraryStore.kt:80-95, run on every
        foreground start) were trial conveniences. Consider dropping the seeding once the trial
        ends, so the production path has no hard-coded content.

I12 Test gaps worth closing with the fixes above: upstream radio drop and recovery (playing and
    paused); http→https redirect for video streaming; skip-on-error in a playlist; the L4 date
    strings; multivariant HLS variant choice; .m3u/.pls wrappers.
